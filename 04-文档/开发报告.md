## 一句话总览

【事实】一个从"记录公司现金及银行钱流向和余额"起步的自用资金管理软件，一路长成"多公司、多币种、集团合并、账套打包、云盘备份"的合资金账 FundMerge，版本从 v1.0 滚到 v5.0.1；【事实】你总结的规律是——v1–v3.4 全是"要新能力"，v4 之后变成"修口径、修性能、修体验"，功能面在 v3.4 就基本铺满，后面都是还债。

## 构想与选型

### 最初设计
【事实】v1.0 = 单公司资金流水 + 账户余额，数据模型最早只有"账户 + 流水"。【事实】数据最初存浏览器 localStorage，后来你要求"完全离线 exe"，才追加 Electron + NSIS 打包。

### 核心使用场景
【事实】日常记账、看余额、出报表、管往来款、做预算、多公司合并、换电脑能整套搬走、云盘自动备份。【推断】核心用户就是你自己（和可能一起做账的人）。

### 技术选型及考虑
【事实】Electron 打包 Windows 桌面软件；前端零框架零构建、五个脚本顺序加载、不引 ES module；数据落本地 `data/data.json` + `files/`，不联网不上传；密码 PBKDF2-SHA256 加盐、云盘凭据 safeStorage 加密、账套包 PBKDF2(120k)+AES-256-GCM；`data-action` 事件委托。【事实】选 Electron + 原生 JS 是因为"最通用，AI 提醒使用"。

### 放弃的方案
【事实】多币种讨论过"账户级/流水级/账套级"，最后选账户级，理由改动面可控。【事实】v3.3.0 同版试过安卓，结论是工具链不完整且无设备验证，**不交付未验证的财务软件**。

### v1.0（时间待回忆）— 记录公司现金及银行钱流向和余额

- **背景**：【事实】触发类型=用户初始需求。你的原话构想："帮我开发一个记录公司现金及银行钱流向和余额的软件"。
- **改了什么**：【事实】单公司资金流水 + 账户余额。
- **当时怎么想 / 触发原因**：【事实】要解决的问题：手工/Excel 记流水、余额算不准。
- **遇到什么问题 → 代价**：【事实】余额公式必须一次定对。当时定的「期初 + 收入 − 支出 − 转出 + 转入」到 v5.0.1 一个字没改。代价：单公司、无权限、数据存浏览器 localStorage——后来你要求"完全离线 exe"，才追加 Electron + NSIS。
- **结果如何**：【事实】余额公式沿用至今。
- **现在回看**：【事实/你的规律】九版里这一版是"用户初始需求"驱动的第一版。

### v2.0（时间待回忆）— 从"记流水"跨到"真做账"

- **背景**：【事实】触发类型=用户需求清单。
- **改了什么**：【事实】外借款 + 未报销（往来款）、货币改塞地、页面要"大厂感"、分类可编辑、预算、现金流量表、对账单、登录与用户。
- **当时怎么想 / 触发原因**：【事实】要解决的问题：单记账不够用——应收应付管不住、支出无约束、没有对外报表、谁都能改。
- **遇到什么问题 → 代价**：【事实】问题最重的一版，从"记流水"跨到"真做账"。代价：单文件 app.js 被迫拆成五层（core/ui/views/modals/app），这个分层一直沿用到今天；同时引入鉴权，会话只存内存。
- **结果如何**：【事实】五层分层沿用至今。
- **现在回看**：【事实】为什么这版定塞地？你的原话："**因为最开始没有考虑完全**"（一开始没考虑多币种，直接把货币定成塞地）。

### v3.0（时间待回忆）— 多公司账本 + 集团总览

- **背景**：【事实】触发类型=用户需求。
- **改了什么**：【事实】多公司账本、集团总览与集团报表。
- **当时怎么想 / 触发原因**：【事实】一个人管几家公司，每家独立记账，另有主面板合并看集团；要能"单看一家"也能"合并看集团"。【事实】多公司是哪来的？你的原话："**后面想到再加纳的公司**"。
- **遇到什么问题 → 代价**：【事实】复杂度暴涨的起点。为了不改写 v2 全部视图代码，用了 `Object.defineProperty` 把 `DB.transactions` 代理到当前公司——省了当时几天的重构，代价是后面每次新增账本数组都必须记得加进 `COMPANY_KEYS`，漏了就静默 undefined。
- **结果如何**：【事实】奠定"公司/集团"两层结构。
- **现在回看**：【事实/你的规律】"每版省下的重构，后面都要加倍还"——代理属性省了 v3.0 改写，代价是 v5.0.0 排查"8 处 DB.companies 口径不一致"。

### v3.0.1（时间待回忆）— 纯 CSS 视觉统一

### v3.1.0（时间待回忆）— 动效、3D 氛围、集团名称

- **背景**：【事实】触发类型=用户三条反馈。
- **改了什么**：【事实】动效、3D 氛围（three.js）、集团名称（关注提醒也在这一线落地）。
- **当时怎么想 / 触发原因**：【事实】三条反馈：①切页卡顿无动效 ②页面单调没突出点 ③无法设集团名称（并建议试 three.js）。
- **遇到什么问题 → 代价**：【事实】这版的判断值得记：卡顿不是动画写错了，是 **v2 为防 GPU 崩溃把硬件加速永久关了**（disableHardwareAcceleration → 全程软件渲染）。改法是"默认开启 + 崩溃自愈"（启动写标志、窗口显示成功就删、下次发现标志才降级）。同一个思路在 v5.0.1 被复用成"显卡状态探测 + 流畅模式"。代价：动效当时做得散，v4.1 才令牌化；three.js 的 3D 层从这版起就是性能负担，直到 v5.0.1 才做上下文复用。
- **结果如何**：【事实】动效/3D/集团名称落地。
- **现在回看**：【事实/你的规律】"用户的'卡'几乎都能追到一个具体的技术决定"——v3.1 的卡追到硬件加速开关。

### v3.2.0（时间待回忆）— 公司档案（资料、账号凭证、文件）

- **背景**：【事实】触发类型=用户需求。
- **改了什么**：【事实】每家一份独立档案，能传 Word/PDF/Excel/图片，记公户账号、网银密码、GRA，上传可自定义名。
- **当时怎么想 / 触发原因**：【事实】财务数据之外，公司注册资料/账号凭证/证照无处安放。
- **遇到什么问题 → 代价**：【事实】关键取舍：文件只存元数据、二进制单独落盘，数据文件保持小体积。另一个取舍是密码明文存本地（离线、不上传），理由写明了——"复制 data.json 即备份"的迁移路径会因加密而失效。
- **结果如何**：【事实】公司档案成为核心模块，v5.0.0 又加"账号卡片"聚合。
- **现在回看**：【推断】"密码明文存本地"是一个明知有风险、但为了离线迁移路径而做的取舍。
