# 合资金账 v4.7.1 安全审计（STRIDE + OWASP）

范围：assets/*.js、electron/main.js、preload.js、backup.js、manual.html。方式：源码静态审计 + 关键路径代码级复现；未做运行时渗透与穷尽 XSS 测试。

## ① STRIDE 威胁表

| 威胁 | 影响 | 现状防护 | 评级 |
|---|---|---|---|
| Spoofing 冒用账号 | 以他人或管理员身份记账 | PBKDF2-SHA256/120k/随机盐（有效）；但最高管理员初始口令硬编码 core.js:1171 且印在 manual.html:166，data.json 内 hash 可被直接替换 | 高 |
| Tampering 篡改账目 | 金额流水被改后无法识别 | 原子写入 + data.bak；无完整性校验、无签名 | 高 |
| Repudiation 否认操作 | 审计日志不可作证据 | auditLogs 记录用户与前后值（有效）；但与账本同文件、可整段删除 | 中高 |
| Info Disclosure 泄露 | 拷走 data.json + files/ 即全量泄露 | 无加密（safeStorage 仅用于云盘凭据） | 高 |
| Elevation 越权 | 记账员看/改全部公司 | allowedCompanies() 仅在渲染层判断，且 fail-open | 高 |
| Denial of Service 数据丢失 | 卸载或覆盖安装后账本+附件被删，无法恢复 | 无。数据目录位于 `$INSTDIR\data`（main.js:60），卸载器 `RMDir /r $INSTDIR` 无条件删除；`deleteAppDataOnUninstall:false` 只保护 `%APPDATA%\FundLedger`，未覆盖账本路径（已与 QA 交叉验证） | 高 |

## ② 关键风险

1. **权限 fail-open（高，core.js:1204/1206）**：`!ids.length` 直接返回全部公司，且过滤结果为空时又回退全部。未配公司的记账员、或被删公司的旧授权 → 看到全集团账目。必须改 fail-closed。
2. **内置管理员口令随安装包分发（P0，已复现，与 QA 独立复现一致）**：同一组最高管理员账号与明文口令出现在三个随包文件里——`assets/manual.html:166`（→`操作手册.html`）、`开发交接说明.md:255/420`、`需求解读与实施方案.md:234`；三者均由 `package.json` 的 `extraFiles` 落进 `$INSTDIR`，且在 `dist18/win-unpacked` 中实际存在。另有第四份副本在 `app.asar` 内（`core.js:1171` 常量，asar 非加密容器，QA 已实际解包提取）。
   **升级为「后门」而非「默认口令」的关键路径**：`app.js:1519` 的 `del-user` 只拦「不能删自己」「至少保留一个管理员」，**没有 `builtin` 保护**；删掉内置账号后重启，`ensureMasterAccount()` 会用同一常量重建该账号 → 用公开口令即可重新以管理员登录。修法：删常量、`ensureMasterAccount` 改为「仅当库中无任何 admin 时引导创建」、`del-user` 增加 `builtin` 拦截、首启强制改密。
3. **权限没有真实边界（高，属设计取舍）**：main.js:341 `store:save` 不校验调用者与内容，`store:load` 返回全库（含所有用户 salt/hash）。改 data.json 或调 window.desktop.save() 即可自造 admin、改任何账目。结论：应用层权限只能防误操作，真正边界是 Windows 账户——必须写进手册告知。
4. **「记住密码」防护强度≈0（低-中）**：AES-GCM 实现正确，但随机 secret 与密文同存 localStorage（app.js:756/777）。只能防"看到屏幕的人"，防不住任何能读该 Windows 配置目录的人。建议密钥移到主进程用 safeStorage。
5. **登录无失败锁定/延时（中，已由 QA 全仓检索确认：无 attempt 计数；密码最短 6 位无复杂度要求）**——共用电脑场景可离线爆破弱口令，PBKDF2 120k 对 6 位数字口令不足。注意：能读 data.json 者可绕过登录，故该项收益有限，定级中而非高。

6. **卸载/覆盖安装删除账本（高，数据完整性与可用性）**——见 STRIDE 表末行。对资金账本软件而言数据丢失等同最高损失，且用户会默认「有 data.bak 和云盘备份」，实际覆盖安装是静默执行旧卸载器后删除。建议数据目录迁到 `%APPDATA%\FundLedger\data`，或自定义 NSIS 卸载段保留 `data`，并在升级前强制自动导出一份。

7. **安装目录可写 + 静默换库（高）**：`nsis.perMachine:false` 默认装到 `%LOCALAPPDATA%\Programs`，该目录当前 Windows 用户可写 → 任何本机进程可改 data.json，且无完整性校验。若用户在安装器中改选 `C:\Program Files`（`allowToChangeInstallationDirectory`/`allowElevation` 均开启），`canWrite()` 失败后 main.js:62 静默回落到「文档\资金台账」→ 用户重装后看到空账本、旧数据留在旧目录，极易重复录入造成账实不符。

8. **文档与实现相互矛盾（P1，降低攻击门槛）**：`manual.html:171` 对用户声明「该账号由程序自动维护，不能被删除或降级」「初始密码随交付单独告知」，但同页 `:166` 就把口令印在表格里，且 `app.js:1519` 实际允许删除。三处互相打脸的结果是：攻击链从「需要读源码」降到「读随包手册即可」，而这个后门在测试中长期未被发现，正是因为手册的可信度掩盖了实现差异。**结论：文档不能作为安全验收依据，只以行为为准。**

9. **云盘备份是 gzip 明文，且允许 http:// 传输（高，已代码确认）**：`backup.js` 的 `buildBundle()` 把 `data.json` 与 `files/` 附件打包成 JSON 后仅 `zlib.gzipSync` 压缩即上传（`application/gzip`），**无任何加密**——拿到备份文件 gunzip 即得全部账目与附件。这把暴露面从「本机文件系统」扩大到「第三方云服务 + 跨境传输」。更严重的是 `request()` 里 `u.protocol === 'https:' ? https : http` 允许明文 HTTP，而 WebDAV 用 Basic 认证（`basicAuth()` 直接 base64），用户若填 `http://` 地址则凭据与账本全程明文过网。建议：备份包用口令派生密钥加密（可复用现有 PBKDF2）、强制 https 并拒绝非 TLS 地址、手册明确披露「备份文件为 gzip 明文」。

10. **预留问题在内部人威胁模型下是弱通道（中高，设计层）**：`SECURITY_QUESTIONS` 为「母亲的姓名」「第一所小学」等客观事实题，在家族企业里老板的亲戚、司机、老员工普遍知道。强制预留问题解决了「锁死」，却把越权通道从「随包 HTML」挪到「熟人知识」。建议按模式分流：**单机模式**保留预留问题自助重置；**多用户/权限模式禁用自助重置**，只能由另一名管理员在设置页重置并写日志——在真正需要内控的场景里直接消灭这条通道，比提高题库质量更有效。若保留自助重置，则需允许自定义问答、答案最小长度、重置后首登弹窗告知、连续失败锁定留痕。

11. **审计日志不可追责（中高，设计层）**：`logAction()` 的字段（`core.js:1214-1237`）无 `hash`/`prevHash`，全无完整性校验；且 `core.js:1236` 在超过 5000 条时执行 `slice(-4000)`，**程序自己会静默丢弃最早 1000 条记录**。两者叠加的后果：日志既不能防篡改，也不能保证完整——「日志可导出 CSV 作证据」「重置动作可追责」这类对外表述不成立，须改写为「操作留痕」。若要支撑追责，必须同时做哈希链 + 链头锚点外存 + 归档而非丢弃。

12. **关键账号路径仍无审计（高，A09）**：全仓 `logAction()` 共 23 处调用。**4.7.2 已修复用户编辑审计**（`modals.js` 编辑分支现记录角色/状态/授权公司的前后差异，质量合格，此项 PASS）；但以下四条仍无任何记录：
   - **改自己密码**（`openPasswordModal()` 仅 `saveDB()`）
   - **管理员重置他人密码，且不需要原密码** —— 最高危：可静默接管任意账号且不留痕
   - **删除用户**（已有 `builtin` 拦截，但无 `logAction`）
   - **找回密码自助重置**（`resetPasswordBySecurity()` 路径）
   后果：账号被静默接管、权限被静默放大，事后均无法发现。这使「权限为内控辅助」的定位失去支撑——内控的前提是有记录。

## ④ 交付物卫生（已复现）

- `dist/win-unpacked/data/data.json`（29KB）含演示账本：示例贸易有限公司、30 笔流水、GHS 币种、加纳银行账户（已掩码）、管理员账号及哈希。**非真实客户数据**（判断依据：币种 GHS、Accra/Kumasi 地名、演示公司名），故不构成客户数据泄露，但随包分发会让用户首次打开看到"别人的账"。当前 4.7.1 的 `dist18/win-unpacked` **不含** data 目录，该问题属旧构建（15:03 的 `dist/`，资金台账.exe）。
- `dist18/win-unpacked/debug.log`（444B）：crashpad 注册失败日志，内容无敏感信息（仅 `registration_protocol_win.cc` 报错），但**证明该产物在构建机上被实际运行过**。定低，但必须清理并加断言——运行痕迹随包发出会暴露构建环境细节，也说明打包流程缺少「构建后不运行」的纪律。推论：构建机若运行过 exe 且数据目录回落，可能在「文档\资金台账」留下账本残留（不在产物内，不随包发，但团队应知晓）。
- 已落地可执行门禁：`deliverables/pack-scan.js` + `pack-scan.rules.json`（QA 交付，实测 4.7.1 产物 FAIL 6 项：debug.log、两份开发文档、两处口令落点 + asar 内常量）。注意 CI 集成陷阱：`node pack-scan.js dist18 | tail` 会把退出码变成 `tail` 的 0，必须直接取 node 退出码或用 `PIPESTATUS`，否则门禁静默失效。
- 建议加打包断言：`win-unpacked` 出现 `data/`、`*.bak.json`、`data-location.txt`、`debug.log` 即构建失败。

现状补偿项：30 分钟无操作自动退出、11 处破坏性操作随机 4 位确认（仅为防误触，非安全边界）、附件路径 resolve 前缀校验有效。

## 结论与前置条件

**判定：No-Go。** 阻断理由按严重度排序：① 管理员明文口令随包分发（4 条路径）② 数据目录在 `$INSTDIR`（卸载即删 + 静默换库）③ `allowedCompanies` fail-open ④ `store:save` 无校验。

**修复前置条件（需产品/用户书面确认）**：`开发交接说明.md:420` 记载「内置管理员账号是用户明确要求写死的，不要删改」。即 P0 第 1 项的修复与既有需求直接冲突，开发不能单方面改，否则会出现「改完又被要求改回去」。

安全侧建议的结构性方案（同时满足「账号固定」诉求与消除后门）：**不要在口令上打补丁，而是把内置账号退出常规登录入口**——
- 首启向导创建 **owner 账号**（强制口令 + 强制预留信息），作为日常最高权限账号
- 内置账号退为「本机维护模式」入口，且该入口不持有任何固定凭据：改为「OS 提权确认 → 生成新的 owner 口令并一次性展示」的授权动作，无口令可泄露
- `ensureMasterAccount()` 的「永不删除」保留为救砖通道，但不再是被普通员工可用的后门
- 若必须保留固定账号名，则至少「写死的是账号、不写死口令」

**该方案的有效性边界（必须说清）**：OS 提权只在「员工使用独立非管理员 Windows 账户」时构成边界。SME 常见做法是全店共用一个管理员 Windows 账户——此时提权确认只是速度障碍，不是安全边界。这与 data.json 可改是同一个根因，只能靠披露 + 操作系统账户治理解决。

## ⑤ 发版前自动化扫描（已落地为可执行门禁）

人工核对只能挡住这一次，下个版本仍会漏。规则已由 QA 落地为可执行门禁：`node deliverables/pack-scan.js dist18`，退出码非 0 即禁止发版；规则与豁免 schema 见 `deliverables/pack-scan.rules.json`。**4.7.1 产物实测 FAIL 6 项，全部为真问题、零噪声。**

**规则设计上的两条硬要求（v1 原样执行会产生 100+ 误报，规则会被开发关掉）**
1. 关键词类规则必须写成「键名 + 6 位以上字面量」的**凭据字面量**规则，不能只匹配 `password|token|secret` —— 后者在 4.7.1 产物上命中 103 项，90+ 是 `cfg.webdav.password`、`refresh_token` 等合法变量名与 `<input type="password">`。
2. 开发者路径必须用反斜杠限定 `\\Desktop\\`，否则命中 `preload.js` 的 `isDesktop: true`。
3. A 类已判死的文件不再重复报 B 类，避免同一问题计数两次淹没真信号。

**A. 产物结构断言**：禁止 `data/`、`data.json`、`data.bak.json`、`data.conflict-*.json`、`data-location.txt`、`files/`、`debug.log`、两份开发文档、`*.map`；顶层条目白名单校验。

**B. 文本扫描**（`win-unpacked` 与 asar 解包目录同时跑，双路径都要修）：凭据字面量、面向用户文档中的口令值、开发者本机路径、手机号形态（命中需人工确认）。

**C. 版本一致性断言**：asar 内 `package.json` 的 version 必须等于安装包版本。已实测有效——对旧 `dist` 跑出 `asar=3.4.1 / 安装包=4.7.0`，并同时抓到 `data/` 与旧产品名 `资金台账.exe`。二进制 grep 不可靠，必须 `asar extract` 后扫文本。

**D. 例外管理**：白名单豁免须写入规则文件并走 review，禁止就地忽略；脚本与规则一并入库。

**门禁有效性证明（自检 6 例，规则 v4，2026-10-28 实跑复核）**
- `sh pack-gate.sh --self-test` → PASS，exit=0：① 含违规项必 FAIL ② 干净产物必 PASS ③ 版本混用被 C 规则拦住 ④ **明文凭据被 `cred-literal` 拦住**（夹具 `password: 'abcdefg'` 被命中）⑤ 合法豁免（file/ruleId/reason/reviewer/date 四要素齐全）放行 ⑥ **豁免缺 reviewer 仍判失败**
- `sh pack-gate.sh dist19` → exit=1，输出「[门禁] FAIL — 禁止发布」（4.7.2 产物被正确拦截，FAIL 3 项）
- 引用自检结论时必须带**规则版本号与日期**：用例集会演进（3 例 → 6 例），不标版本则无法判断当时验了什么
- **CI 集成陷阱**：`node pack-scan.js dist18 | tail` 的退出码是 `tail` 的 0，门禁会静默失效。已由 `pack-gate.sh` 包装器解决（输出先收进变量、不接管道、原样透传 node 退出码），两种模式（正式扫描 / `--self-test`）都生效
- **已知残余限制**：自检能证明「规则会拦住这类违规」，不能证明「规则没漏掉某类违规」（例如有人给 `cred-literal` 加文件级白名单，自检仍全绿）。只能靠规则变更强制 review + changelog（`pack-scan.rules.json` 已按 v1→v4 留痕，每条含 `selfTest: yes/no` 强制字段）
- **规则指纹（防夹带改动）**：指纹 = `sha256(rules.json + pack-scan.js)` 前 16 位，与入库的 `pack-gate.expected` 比对，不一致即 FAIL。改动规则或匹配逻辑必须在同一提交执行 `--update-expected`，评审 diff 中可见。实测：仅给 `pack-scan.js` 加一行注释即被拦截（有意为之——注释不改行为，但证明文件被动过）
- **该机制的防护等级（必须写清，勿夸大）**：它防的是**无意改动与夹带改动**，不防**有意绕过**——能修改脚本的人同样能修改 expected 文件。防恶意需依赖 git 提交历史、分支保护、CI 从干净 checkout 运行。不要把这套当成防内鬼机制
- **未闭合的一环：指纹绑定的是规则，不是产物**。当前可证明「规则没被改」，但不能证明「这个安装包是用这套规则扫过的」。建议发版时生成 sidecar：`FundMerge-Setup-x.y.z.scan.json`，含安装包 SHA-256、规则指纹、FAIL 计数、扫描时间，随发版归档。三者绑定后，事后才能回答「某个已发出的包当时是否通过、用哪版规则」

**人工确认项（不自动化）**：构建完成后检查构建机 `%USERPROFILE%\Documents\资金台账` 是否存在 `data.json`。`debug.log` 证明产物在构建机上被运行过，若当时数据目录回落到文档目录，构建机可能残留账本。

## ⑥ 修复方案的安全评审（修复本身引入的新风险）

修复方向已定稿（B0 凭据与权限 / B1 账本位置），但其中若干项会引入新的风险面，必须在实现时一并处理，否则是把一个洞换成另一个洞。

| # | 修复引入的新风险 | 处置要求 |
|---|---|---|
| R1 | 多用户模式关掉自助重置后，唯一管理员忘口令即锁死 | 要求 ≥2 个管理员；**禁止删除最后一个管理员**（负向用例）。但这是防锁死机制，**不是双人复核**，不得在手册暗示「双管理员 = 双人审批」 |
| R2 | 应急管理员账号成为第二个凭据攻击目标 | 应急账号任何登录/重置均强制留痕，并向主账号弹窗告警；凭据由客户离线保管 |
| R3 | 管理员重置他人口令后可静默使用 | 被重置账号**下次登录必须立即改密**才能进入，仅「弹窗告知」不足 |
| R4 | 维护模式是**无凭据的提权入口**，本地接触者可将老板锁在账本外 | **已决定 4.7.2 不做维护模式（延后至 4.7.3），R4 与 R2 随之消失** —— 攻击面收敛，安全侧支持该决定。但必须补 R9 |
| R9 | 砍掉维护模式后，「救砖」变成无正式通道，支持团队会私自改 `data.json` 重置 | 那条路径**无审计、无授权、无留痕**，比维护模式更糟，且与攻击者路径完全重合。要求：① 多用户模式强制预留信息（已定）② 首启强制导出一次完整备份到**用户指定的外部位置**（非 `%APPDATA%`，避免同盘故障）③ 内部支持流程书面化：「客户提供 data.json → 技术支持生成重置补丁 → 客户知情并签字」，禁止口头救砖 |
| R5 | 「引导用户选择数据目录」可能选到 OneDrive/坚果云等同步目录，把明文账本同步上云 | 检测常见同步目录时给出明文风险提示，并要求二次确认 |
| R6 | B1-7 升级快照会累积多份明文账本副本，扩大泄露面 | 限制份数（3 份）且界面可查可删；受与主账本相同的披露约束 |
| R7 | 单机模式「无口令」使审计日志无法归因，留痕价值归零 | 单机模式至少要求选择/填写操作人显示名（无密码），保证日志可归属 |
| R8 | **降级通道被自己的修复关掉**：4.7.2 把数据搬到 `%APPDATA%`，旧版读不到；且降级必须先卸载 4.7.2，其卸载器仍 `RMDir /r $INSTDIR`，会连带删掉「保留的原件」 | 「保留原件」不解决降级。建议 4.7.2 提供「导出 4.7.0 兼容包」+ 明确操作指引，并在发版说明写清降级步骤；仅在 `%APPDATA%` 留快照不足以让旧版自动读到 |

## ⑦ 4.7.2 复扫结果：P0 未修复，且告知被削弱

对 `dist19`（4.7.2）实跑 `pack-scan.js`：**FAIL 3 项**，结构断言与版本一致性通过（`asar=4.7.2 / exe=4.7.2`），但三项全部指向同一件事——**凭据仍在包里**：

- `asar/assets/core.js` 的 `MASTER_ACCOUNT` 常量仍含明文口令（`cred-literal`）
- 同一常量与 `操作手册.html` 的账号行为真实手机号（`phone`，已升为 fail）

已确认的部分修复：`extraFiles` 已移除两份开发文档、`manual.html` 不再印口令、产物无 `data/` 与 `debug.log`。

**但这不是修复，是把「可发现」变成「不可发现」，且引入了两个新问题：**

1. **文档再次不实**：`开发交接说明.md:255/420` 与 `需求解读与实施方案.md:234` 现写成「初始口令，**不入库不入包**」——事实上口令仍在 `app.asar` 内，解包即得。「不入包」这句话是假的，与之前「随交付单独告知」属同一类问题：文档声明了一个它并未满足的安全属性。
2. **合法用户被锁在门外，攻击者不受影响**：`manual.html:166` 改为「（见交付说明，首次登录后请立即修改）」，而「交付说明」（开发交接说明.md）已不在 `extraFiles` 中、不随包分发。结果是：普通用户找不到初始口令、无法登录内置账号；能解包 asar 的人仍然拿得到。**修复的不对称性使实际安全水位没有提高，可用性反而下降。**

**结论：P0 第 1 项在 4.7.2 中未修复，判定维持 No-Go。** 正确修法仍是删除常量本身（口令不进入产物），而不是删除告知。
