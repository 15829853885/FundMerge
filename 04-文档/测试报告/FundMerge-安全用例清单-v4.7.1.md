# FundMerge v4.7.1 安全用例清单（可复现步骤）

编写：QA Lead ｜ 依据：gstack-security-officer 定级意见 + 源码核对
适用范围：合资金账 v4.7.1（Electron 45 / electron-builder 26.18.0，NSIS 安装包）
数据文件：`<安装目录>\data\data.json`（`electron/main.js:46` `APP_DIR = dirname(exe)`；安装目录不可写时回落 `%USERPROFILE%\Documents\资金台账`）

> 说明：每条用例给出「预期（应有行为）」与「现状判定（源码推断）」。凡标 **待实测** 的，需在真机跑一遍确认；标 **已确认** 的，已由源码路径锁定，实测用于留证。

## SEC-01 记账员 `companyIds` 为空数组 → 是否可见全部公司（高危 fail-open）

- **严重度**：P0（越权读取全集团资金数据）
- **前置**：管理员已建 3 家公司（A/B/C），各 1 笔流水；已建记账员 `staff01`
- **步骤**
  1. 管理员登录 → 用户管理 → 编辑 `staff01` → 公司授权复选框**全部不勾** → 保存
  2. 打开 `<安装目录>\data\data.json`，确认 `users[].companyIds === []`
  3. 退出，用 `staff01` 登录
  4. 观察左侧公司切换器条目数；进入「集团总览」「集团报表」看合计口径
  5. 在集团总览点「查看明细」（`drill-open`）任选一家未授权公司
- **预期（应有）**：`companyIds=[]` 应解释为「无任何公司权限」，登录后公司列表为空或明确提示「未授权，请联系管理员」
- **现状判定（已确认）**：`core.js:1199-1206` `allowedCompanies()` 中 `if (!ids.length) return DB.companies;` → **空数组回退为全部公司**，staff01 可见 A/B/C 全部账目。步骤 5 亦无 `canAccessCompany` 校验（`app.js:1274-1281`），可直接进入任意公司流水页
- **结论**：安全边界写反了（fail-open），且「不勾选」在 UI 上是最自然的「禁止访问」操作

## SEC-02 被授权公司全部删除后 → 是否回退「看到全部公司」

- **严重度**：P0（同 SEC-01，且由正常业务操作触发）
- **前置**：`staff01` 仅授权公司 A；A 下有流水
- **步骤**
  1. 管理员登录 → 公司管理 → 删除公司 A（确认码）
  2. 查看 `data.json`：`users[staff01].companyIds` 是否仍残留 A 的 id
  3. 用 `staff01` 登录，观察可见公司数
- **预期（应有）**：无有效授权 → 不可见任何公司数据
- **现状判定（已确认）**：`allowedCompanies()` 末尾 `return list.length ? list : DB.companies;`，`list` 为空即回退全部 → **公司被删后权限从「1 家」放大到「全部」**
- **备注**：删除公司时未见清理 `users[].companyIds` 的逻辑，属权限数据未级联

## SEC-03 直接编辑 `data.json` 把 staff 提权为 admin

- **严重度**：P0（认证与授权完全依赖可编辑的明文文件）
- **步骤**
  1. 完全退出程序（托盘退出，确认进程结束）
  2. 备份 `data.json`
  3. 用记事本/VSCode 打开 `data.json`，把目标用户 `"role": "staff"` 改为 `"role": "admin"`，保存
  4. 启动程序，用该账号登录
  5. 观察侧栏是否出现「公司管理/用户管理/操作日志/云盘备份」，能否删除流水
- **预期（应有）**：数据文件被非程序修改应被检测（完整性校验/签名），或角色变更需管理员会话内操作
- **现状判定（已确认）**：`verifyLogin()` 只校验密码哈希，`startSession()` 直接取 `user.role`（`core.js:584-601`）；`electron/main.js` 全仓无 checksum/HMAC/签名校验 → **改一个字符串即获得管理员**
- **衍生**：既然 `hash`/`salt` 同样可改，攻击者可写入自己计算的 PBKDF2 值（算法与迭代数在源码可见）→ 无需知道原密码即可接管任意账号
- **修复建议**：对 `data.json` 的 `users[]` 段做 HMAC（密钥经 `safeStorage`/DPAPI 存 `%APPDATA%`），启动时校验失败则拒绝进入用户管理

## SEC-04 覆盖安装后 `data` 目录与附件是否仍在

- **严重度**：P0（数据丢失，非泄露）
- **前置**：`dist/FundMerge-Setup-4.7.0.exe`（文件版本 4.7.0）；4.7.2 尚未构建，用 4.7.1 覆盖 4.7.0 等价
- **步骤**
  1. 全新安装 4.7.0（**必须用 exe 安装，勿用 `dist/win-unpacked`——其 app.asar 内是 3.4.1，基线错误**）
  2. 建 3 家公司、各若干流水、1 个公司档案附件、记录凭证号最后一位
  3. 完全退出程序；记录 `<安装目录>\data\` 的文件清单与大小
  4. 双击 `FundMerge-Setup-4.7.1.exe`，装到**同一目录**覆盖安装
  5. 安装完成后检查 `<安装目录>\data\` 是否仍存在、`files\` 下附件是否还在
  6. 启动程序，看账本是否为空、凭证号是否续号、附件能否打开
- **预期（应有）**：覆盖安装不触碰 `data\`；升级后账本完整、凭证号连续、附件可打开
- **现状判定（已确认，源码级）**：
  - 覆盖安装时安装器先静默执行旧卸载器：`app-builder-lib/templates/nsis/include/installUtil.nsh:224` `ExecWait '"old-uninstaller.exe" /S /KEEP_APP_DATA --updated _?=$installationDir'`；同文件 166 行注释原文："uninstaller should be copied out of app installation dir (**because this dir will be deleted**)"
  - 卸载器 `uninstaller.nsh:187` `RMDir /r $INSTDIR` **无条件递归删除**；`/KEEP_APP_DATA` 在模板中无任何消费方（全文仅出现于传参处）
  - `package.json` 的 `nsis.deleteAppDataOnUninstall:false` 只保护 `%APPDATA%\FundLedger`（`uninstaller.nsh:232-248`），账本不在该路径 → **保护无效**
  - **预计结果：`data\` 连同账本与附件被删除，启动后为空账本**
- **变体 4a（更隐蔽）**：设置 → 更改数据目录到 `D:\FMData` → 覆盖安装 → 检查 `<安装目录>\data-location.txt`（`main.js:600`）是否被删。若被删，应用回落 `$INSTDIR\data` 新建空账本，而真实数据仍在 `D:\FMData`，用户无法自行找回
- **变体 4b（纯卸载）**：4.7.1 造数据 → 卸载 → 检查 `data\` 是否被删（同源问题，`RMDir /r $INSTDIR`）

## SEC-05 管理员改密后重启，`ensureMasterAccount()` 是否重置密码

- **严重度**：需分两问，结论不同
- **问题 A：改密后重启是否被重置？**
  1. 用内置账号 `15829853885` 登录 → 修改密码为 `Test@12345`
  2. 完全退出 → 重启
  3. 用旧密码登录（应失败），用新密码登录（应成功）
  - **预期**：新密码生效，不被回滚
  - **现状判定（已确认）**：`core.js:1173-1186` 的 `exist` 分支只修正 `role`/`companyIds`/`security` 三个字段，**不触碰 `salt`/`hash`** → 改密不会被重置。此项**不构成缺陷**
- **问题 B：删除内置账号后重启会怎样？（真正的风险）**
  1. 用另一管理员账号登录 → 用户管理 → 删除 `15829853885`（`app.js:1519` 的删除逻辑无 `builtin` 保护，仅拦「最后一个管理员」）
  2. 完全退出 → 重启（`app.js:1693/1697` 每次启动调用 `ensureMasterAccount()`）
  3. 用**源码中的硬编码口令**（`core.js:1172` `MASTER_ACCOUNT`）登录
  - **预期（应有）**：内置账号不可删除，或删除后不以固定口令重建
  - **现状判定（已确认）**：账号被删 → 下次启动以 `MASTER_ACCOUNT` 常量重建为 admin，密码回到硬编码值 → **任何读过源码的人可重新取得管理员**

## SEC-06 硬编码内置管理员凭据可被提取（新发现，建议并入审计）

- **严重度**：P0（后门式提权）
- **事实**：`assets/core.js` 中 `MASTER_ACCOUNT` 常量（v4.7.1 约 1171 行）含明文 `password` 字段，形如 `{ username: '15829853885', password: '<明文>', displayName: '刘立志' }`（报告中脱敏；**复核以常量名定位，勿依赖行号——行号随修改变动，写死行号的验收项下个版本即失效**）
- **四条泄露路径**（同一口令，随安装包分发）：
  1. `resources/app.asar` → `assets/core.js` 的 `MASTER_ACCOUNT` 常量
  2. `$INSTDIR\操作手册.html` 第二章「内置最高管理员」表格「初始密码」行（源 `assets/manual.html`）
  3. `$INSTDIR\开发交接说明.md`（两处；其中一处注明"用户明确要求写死，不要删改"）
  4. `$INSTDIR\需求解读与实施方案.md`（"内置最高管理员"条目）
  - 2/3/4 均经 `package.json` 的 `extraFiles` 落进安装目录，与 `asar` 无关，改代码不会自动消除
- **可复现提取**（本机已实际执行成功）：
  1. `npx asar extract "<安装目录>\resources\app.asar" out`
  2. 在 `out\assets\core.js` 中检索 `MASTER_ACCOUNT`，即可读到账号与明文口令
  3. 用该账号口令登录任一安装实例 → 管理员
- **说明**：asar 不是加密容器，仅打包；`asar: true` 不提供任何保密性。该口令在 v3.4.1 与 v4.7.1 两个产物中均存在（已比对）
- **附带文档与实现矛盾（P1）**：`manual.html` 同一张表格内，上一行印着初始口令，下一行注释却写「初始密码随交付单独告知」，5 行之内自我否定；同一处还告知用户「该账号由程序自动维护，**不能被删除或降级**」，但 `app.js` 的 `del-user` 实际允许删除。结论：**文档不能作为安全验收依据，只以行为为准**；也解释了该后门为何历轮测试未被发现
- **修复建议（定稿：按模式分流 + 内置账号退出常规登录入口）** — ⚠ 早期"随机口令+抄写确认"方案**已撤回**，勿再采用（离线单机场景下抄写纸丢失 = 永久锁死，用低概率小洞换高概率不可逆灾难）
  1. **首启选运行模式**：单机（无口令，明示风险）／多用户（强制口令 + 强制预留信息，且**禁用自助重置**，只能由另一管理员重置）
  2. **内置账号退出登录框**，退为维护模式入口，**不持有任何固定凭据**（OS 授权后生成新 owner 口令，一次性展示）
  3. `ensureMasterAccount` 仅在库中无任何 admin 时才创建；`del-user` 保留 `builtin` 拦截（v4.7.2 源码已加）
- **备选方案（降级保留）**：写死账号、不写死口令 —— 保留 `15829853885` 与「不可删除/不可降级」，口令改首启随机生成 + 一次性展示。**仅在方案 1 无法落地时采用**，且必须同时提供"口令遗失后的 OS 级恢复路径"，否则回到锁死风险
- **需产品书面确认**：`开发交接说明.md` 记录"内置管理员账号是用户明确要求写死的，不要删改" → 任何方案均需产品/用户书面确认。**送审时以定稿方案为准**，表述重点为"保留内置账号与不可删除性，仅收回固定口令"
- **验收判据（以机器输出为准，不以文字描述为准）**：
  1. **主判据**：`sh deliverables/pack-gate.sh dist19` 输出 `FAIL 0` 且 `exit 0`。**不接受"已删除硬编码口令"这类文字说明**——文字可被"改文档不改代码"糊弄，退出码不会
  2. **前置**：先跑 `sh deliverables/pack-gate.sh --self-test` 得 `exit 0`，确认门禁本身未被改坏，否则上面的 PASS 无意义
  3. **辅助**：在**安装目录**检索账号串与口令串，确认 `app.asar`、`操作手册.html`、`开发交接说明.md`、`需求解读与实施方案.md` 四处均无残留（门禁已覆盖前两者，人工补后两者所在目录）

## SEC-07 审计日志可篡改、可整段删除、可被程序静默截断

- **严重度**：P1（资金软件的审计不可信，等于无法追责）
- **前置**：管理员登录，已产生 ≥5 条操作日志
- **步骤**
  1. 打开 `data.json`，检查 `auditLogs[]` 每条是否含 `hash`/`prevHash` 字段
  2. 把 `"auditLogs"` 整段改为 `[]`，保存，重启 → 看「操作日志」页是否为空、是否出现任何告警
  3. 还原后改某条日志的 `before`/`after` 金额，保存，重启 → 看是否可检出
  4. 连续造 5001 条日志 → 观察条数变化
- **预期（应有）**：日志被删改时应用告警或拒绝启动；截断行为需显式告知
- **现状判定（已确认）**：`core.js:1214-1237` 写入的日志字段中**无任何哈希/链式校验**；`electron/main.js` 无完整性校验 → 删改后无感知。另 `core.js:1236` 在超过 5000 条时 `slice(-4000)`，**程序自身会静默丢弃最早 1000 条**，用户无从知晓
- **修复约束（security-officer 意见，采纳）**：仅做哈希链不够——整段删除后重新计算即可绕过。必须同时做**链头哈希外存**（`%APPDATA%` 锚点文件，或随云盘备份一并上传），否则是安全剧场
- **验收断言**：删除整段 `auditLogs` 后重启，应用必须告警/拒绝；这条是区分"真防护"与"假防护"的关键用例

## SEC-08 云盘备份为明文 gzip，且允许非 TLS 传输

- **严重度**：P1（备份是离线产品唯一兜底，包内即全部账目+附件）
- **用例 8a 备份包未加密**
  1. 配置任一 WebDAV → 执行一次备份
  2. 取回备份文件，`gunzip` 解压
  3. 用错误口令尝试解密
- **预期**：不解密无法读取；错误口令必须失败且不产生半截文件
- **现状判定（已确认）**：`electron/backup.js` 的 `buildBundle()` 把 `data.json` 全文与 `files/` 下附件以 base64 装入 bundle，仅做 `zlib.gzipSync(json, {level:6})` → **`gunzip` 即得全部账目与附件，无任何加密**。用例现在必然失败，属预期（用于锁住修复）
- **用例 8b 允许非 TLS 地址**
  1. WebDAV 地址填 `http://` 开头 → 保存并测试连接
  2. 抓包观察是否发出明文请求
- **预期**：应被拒绝并给出明确提示，不得发起任何连接
- **现状判定（已确认）**：`request()` 中 `const mod = u.protocol === 'https:' ? https : http` → **会真的走明文 http**，Basic 认证头与账本数据在网络上明文可见

## SEC-09 账号与权限变更审计缺失（内控前提不成立）

- **严重度**：P1（"权限作为内控辅助"的定位依赖留痕，无记录则内控不成立）
- **用例 9a 首启是否强制预留信息**
  1. 全新安装（无 `data.json`）→ 走初始化流程
  2. 不填预留问题直接下一步
- **预期**：不得进入下一步（否则该账号日后无法走"找回密码"）
- **现状判定**：首启初始化分支只校验账号格式、密码长度、两次一致，**不要求预留问题**；自助注册分支却强制两项答案 → 首启管理员 `security` 为空，忘记密码后无自助找回路径
- **用例 9b 账号变更四类动作是否留痕**（逐条查操作日志）

  | 动作 | v4.7.2 源码现状 | 判定 |
  |---|---|---|
  | 编辑用户：改 `role` / `active` / `companyIds` | **已修**：`modals.js` 用户编辑分支已有 `logAction('修改',{module:'用户'})`，并记录「角色/状态/授权公司 前→后」差异 | PASS |
  | 改自己密码 | `openPasswordModal()` 仅 `saveDB(); closeModal();`，**无 `logAction`** | FAIL |
  | 管理员为他人重置密码（不需原密码） | 同上，**无 `logAction`** | FAIL |
  | 删除用户 | `del-user` 已有 `builtin` 拦截，但**无 `logAction`** | FAIL |
  | 走"找回密码"自助重置 | 无 `logAction` | FAIL |
- **结论**：4 项中 3 项仍缺。其中"重置他人密码无需原密码且无日志"最危险——可静默接管任意账号而不留痕
- **修复建议**：四处补 `logAction('修改', {module:'用户', target:'密码重置 <账号>'})`，记录操作人、目标账号、结果；首启强制预留信息或明示"未设置将无法自助找回"

## SEC-10（产品侧 R5）选择同步盘目录时无二次确认

- **严重度**：P1（用户以为只是换本地路径，实际把明文账本上传到云端）
- **步骤**
  1. 设置 → 更改数据目录 → 选择 `OneDrive` / `坚果云` / `Dropbox` / `Google Drive` 同步文件夹
  2. 观察是否弹出二次确认，提示"会把明文账本上传到云端"
- **预期**：必须二次确认并明示风险
- **现状判定**：全仓无同步盘路径识别逻辑，**选择时无任何确认** → 用例 FAIL。更严重的是产品在**教程式引导**用户这么做：`views.js:1363`「把它放进网盘同步文件夹（OneDrive / Google Drive / Dropbox）」、`views.js:1996`「把整个 data 目录放进网盘同步文件夹即可实现跨设备同步」、`manual.html` §15.4 给出完整步骤教程；而同一本手册 §2 安全说明又写「也不要把含密码的 data 放进共享网盘」→ **手册 §15.4 教用户放，§2 叫用户别放**。用户按教程操作即违反手册自身的安全条款
- **定性**：这不是"忘了加检测"，是**产品定位矛盾**。二次确认只能治标，根治需产品决策"是否支持网盘同步"；若支持则必须加密，若不支持则删除教程与引导文案
- **说明**：SEC-04 修复若把数据目录迁到 `%APPDATA%`，本项风险下降但不消失（用户仍可手动指定）

## SEC-11（产品侧 R3）被重置口令后未强制改密

- **严重度**：P1（管理员重置口令后，新旧口令并存期无人管控）
- **步骤**
  1. 管理员 A 重置 B 的口令
  2. B 用新口令登录
- **预期**：**强制跳转改密页并拦截进入业务界面**（不是弹窗提示）
- **现状判定**：无 `mustChangePassword` 类字段，登录后直接进业务界面，**无提示也无拦截** → 用例 FAIL
- **修复建议**：用户模型加一次性标记，登录成功后先跳改密；改密完成才允许进入，并记日志（与 SEC-09 一并做）

## 优先级建议（与 security-officer 定级对齐）

| 顺序 | 用例 | 理由 |
|---|---|---|
| 1 | SEC-04（含 4a/4b） | 数据直接丢失，用户以为有 `data.bak`/云盘兜底 |
| 2 | SEC-06 | 硬编码口令 = 通用后门，拿到 exe 即得管理员 |
| 3 | SEC-01 / SEC-02 | fail-open 越权，正常 UI 操作即可触发 |
| 4 | SEC-03 | 需本机文件写权限，威胁模型较窄，但修复成本低（HMAC） |
| 5 | SEC-08 | 备份明文 + 允许 http，备份链路等于裸奔 |
| 6 | SEC-05B | 与 SEC-06 同源，随 SEC-06 一并修 |
| 7 | SEC-10 / SEC-11 | 修复动作自开的洞，须与对应修复同批测 |
| 8 | SEC-07 / SEC-09 | 审计不可信，修复成本高于前几项，可排次轮 |

**已修复项（v4.7.2 源码核实，供回归确认）**：`del-user` 已加 `builtin` 拦截；用户编辑已记录角色/状态/授权公司差异；产物已移除 `debug.log` 与两份开发 md（A 类结构断言 PASS）。

**发版前自动化门禁**（四层，缺一不可）
1. `npm run dist` — 出包后自动串联门禁（带 `--quarantine`：扫不过则把 `FundMerge-Setup-*.exe` / `.blockmap` 改名为 `.BLOCKED-<时间戳>` 并写 `SCAN-FAILED.txt`，让"扫不过"等于"拿不到可发的包"）
2. `sh deliverables/pack-gate.sh <distDir>` — 手动复核入口，规避管道吞退出码；**同时打印规则文件版本与 sha256 前 8 位，须抄进发版记录**
3. `sh deliverables/pack-gate.sh --self-test` — 门禁自检 6 例：① 违规必须 FAIL ② 干净必须 PASS ③ 版本混用必须被拦 ④ 明文凭据必须被 `cred-literal` 拦 ⑤ 合法豁免（四要素齐全）必须放行 ⑥ 豁免缺 `reviewer` 必须仍 FAIL
4. **人工确认项**：构建机 `%USERPROFILE%\Documents\资金台账` 是否残留账本（`debug.log` 证明产物在构建机被运行过，数据可能落在旧回退路径）；出包后不要在 `win-unpacked` 里直接运行

**规则指纹的意义**：自检 PASS 只证明「当前规则集能拦住已知 6 类违规」，证明不了「规则集没被改松」。记录 sha256 才能事后回答"这次发版用的是哪版规则、谁改的"。规则文件 `changelog` 每条都带 `selfTest: yes/no + why` 字段，用于区分"当时验得不够"与"当时判断不需要验"。

**规则指纹自校验（机器强制，非人工抄写）**
- 指纹 = `sha256(pack-scan.rules.json + pack-scan.js + pack-gate.sh)` 前 16 位，写入 `deliverables/pack-gate.expected`
- 门禁启动即比对：不一致直接 FAIL，并打印期望值与实际值
- 改动门禁行为必须**在同一提交里**执行 `sh deliverables/pack-gate.sh --update-expected`，改动因此留在 diff 里；若不是你改的 → 说明门禁被绕过，须立即排查
- 纳入 `pack-scan.js`：匹配逻辑（正则、去重、`isValidExemption`）在脚本里，只改脚本时旧设计指纹不变而行为已变
- 纳入 `pack-gate.sh`：它决定「扫什么」（选目录、是否带 `--quarantine`、是否执行指纹比对），被改动可整套架空门禁
- **已实测**：改 `pack-scan.js` 或 `pack-gate.sh` 任意一个（哪怕只加一行注释）→ 指纹即变、`exit=1`；还原后恢复 PASS

⚠ **防护等级边界（不要当成更强的保证）**：该机制防**无意改动与夹带改动**，**不防有意绕过** —— 能改 `pack-scan.js` 的人同样能改 `pack-gate.expected`，两者同仓同权限。指纹的价值是让「门禁被动过」在 diff 里显形，把决定权交回评审人，**不是密码学意义上的防篡改**。真正的防恶意依赖仓库之外：git 历史与签名、分支保护、**CI 从干净 checkout 运行**。若 CI 在开发者工作区跑，本地改过的脚本会直接生效 —— 此时指纹 FAIL 看着像误报，实际是它工作正常。

**扫描凭证 sidecar（绑定产物，而非只绑规则）**
- `node deliverables/pack-scan.js <dist> --sidecar` 生成 `FundMerge-Setup-<ver>.scan.json`，随安装包归档
- 内容：`packageSha256` + `rulesFingerprint` + `rulesVersion` + `result`（PASS / FAIL-n）+ `scannedAt`
- 解决的问题：指纹只证明"规则没被改"，证明不了"这个包是被这套规则扫过的"。sidecar 让三样东西绑定，事后拿到任何一个已发出的包，都能回答"它当时过没过、用哪版规则扫的"
- **失败详情已脱敏**：只保留规则 id 与位置，丢弃 `::` 之后的原始行内容 —— 否则 sidecar 自己会变成新的口令泄露源（已实测 `grep` 口令与手机号 0 命中）
- 4.7.2 实测：`result=FAIL-3`、`rulesVersion=4`、`packageSha256=9425fb853cc5…`

**⚠ 门禁性质：自证型（self-attested），不是独立验证**
- 机制强度 = min(机制强度, 执行环境可信度)。若仅在发版人本地手动执行，执行者与被验证者是同一人
- 因此可以说"**我们建立了检查**"，**不能**说"检查已独立执行"。若出现漏发，这两种表述的责任归属完全不同
- 建议列为 4.7.3 项：CI 从 tag 干净 checkout 构建 + 门禁在其中执行；4.7.2 发版说明应诚实写明当前为自证型

**`--quarantine` 已实测**：临时夹具中 `.exe` 与 `.blockmap` 均被改名并生成 `SCAN-FAILED.txt`；`dist`/`dist18`/`dist19` 三个历史目录的 exe 原样未动（该参数为 opt-in，回归扫描历史产物时不要带）。
