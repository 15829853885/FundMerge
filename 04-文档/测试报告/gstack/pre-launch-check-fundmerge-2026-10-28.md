## 附录 A：评审补充结论（收口后新增）

### A.1 SEC-08 备份包为明文（P1，已确认）

`backup.js buildBundle()` 把 `data.json` 全文 + `files/` 全部附件转 base64 后**只做 gzipSync，无任何加密**。
任何人拿到备份包，`gunzip` 一次即得全部账目与附件原件。
另：`request()` 里 `u.protocol === "https:" ? https : http`，填 `http://` 会真的走明文，Basic 认证头随明文传输。

**影响**：直接推翻"备份是唯一兜底"的产品假设——备份包泄露 = 账本全泄露。
**建议**：备份包用同步口令派生密钥加密（与云同步方案同源），并在 UI 上禁止 http:// 或强提示。

### A.2 SEC-09 账号变更无审计（P1，已确认）

- 首启初始化**不要求设置预留问题**（自助注册却强制要求）→ 首启管理员 `security` 为空，日后**无法自助找回密码**。这是功能缺陷，不只是安全问题。
- 改密、重置密码路径**完全没有 `logAction()` 调用** → 账号被改密无迹可查。

### A.3 对 L6「降级通道被修复关掉」的事实更正

评审意见认为 4.7.2 把数据迁到了 `%APPDATA%\FundLedger\data`，导致旧版读不到、降级即丢库。

**这一条与实现不符，予以更正**：v4.7.2 的修复方式是 `build/installer.nsh` 的 `customRemoveFiles` 宏——
卸载/升级前把 `data` 目录移到 `$TEMP`，`RMDir /r $INSTDIR` 之后再移回 `$INSTDIR\data`。
**数据目录位置没有变，仍在安装目录下**。因此：

- 旧版 4.7.0 仍能读到同一份 `data`，降级不会因路径变化而丢库；
- L6 所描述的"两个修复互相拆台"不成立；
- 但"降级后新版本新增字段旧版不识别"的风险仍然存在，建议发版说明写「升级前请导出 JSON 备份」。

### A.5 维护模式的风险披露（R4）

维护模式（重置管理员口令）**无任何凭据即可触发**。它不降低实际安全水位（`data.json` 本来可被本地修改），

## 附录 C：门禁的性质与边界（放行措辞依据）

### C.1 它是「自证型门禁（self-attested）」，不是独立验证

**门禁的实际强度 = min(机制强度, 执行环境可信度)。**

当前门禁由发版人在本地手动执行 —— 执行者与被验证者是同一个人。机制本身有效（能拦违规、能自检、指纹能发现被改动），
但**不能作为"产物已通过独立验证"的证据**。

| 可以说 | 不能说 |
|---|---|
| 我们建立了发版检查机制 | 检查已由独立环境执行 |
| 本次产物经门禁扫描为 PASS（发版人执行） | 产物已通过第三方验证 |

差别很实际：万一将来漏发，这两种表述的责任归属完全不同。

**改进项（4.7.5）**：CI 从 tag 干净 checkout 构建 + 门禁在 CI 内执行，届时可去掉"自证型"标注。

### C.2 指纹绑定的是规则，不是产物

指纹能证明"规则没被改"，证明不了"这个安装包是用这套规则扫过的"。

**已补：产物 sidecar** —— `FundMerge-Setup-<ver>.attest.json` 随包归档，内含：

```json
{
  "product": "FundMerge-Setup-4.7.4.exe",
  "sha256": "（安装包完整哈希）",
  "gateRuleFingerprint": "cd27453f000d20ee",
  "gateResult": "PASS",
  "gateFailures": 0,
  "attestationType": "self-attested",
  "scannedAt": "（时间）"
}
```

三样（包哈希 + 规则指纹 + 结果）绑定后，事后拿到任何已发出的包都能验证「当时是否通过、用哪版规则」。

### C.3 指纹机制的防护边界（安全官口径，原文保留）

> 指纹防的是**无意改动与夹带改动**，不防**有意绕过** —— 能改脚本的人同样能改 expected 文件，同仓同权限。
> 它的价值是让"门禁被动过"在 diff 里显形，把决定权交回评审人，不是密码学意义上的防篡改。
> 真正的防恶意要靠仓库之外：git 历史与签名、分支保护、CI 从干净 checkout 运行。

### C.4 本轮三条通用原则（建议留进项目规范）

1. **任何「已修复」的声明，都必须附一条能失败的检查；附不出检查的，视为未修复。**
2. **安全修复不能只降低"可被发现的程度"，必须消除凭据本身。**
3. **当两个选项都坏时，说明问题定义错了** —— 好的修复让争论的问题消失，而不是在两个坏选项里选一个。
