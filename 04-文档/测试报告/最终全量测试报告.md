## 四、7 个失败项逐条定位

| 编号 | 表面现象 | 根因 | 结论 |
|---|---|---|---|
| E-12 | `Cannot read properties of undefined (reading 'id')` | 第二家公司建后未建账户，`to.accounts[0]` 为 undefined | **测试数据前置缺失**。补账户后复测通过 |
| G-05 | 版本池 `7→7→7` | 上一轮测试残留的 `backup-index.json` 已有 7 条，非从 0 开始 | **测试环境未清理**。清索引后复测 `1,2,3,4,5,6,7` 全对 |
| I-01 | `NaN KB` | 3 天间隔机制已自动备份过，`autoRun()` 返回 `created:false` | **期望值错误**，产品行为正确 |
| I-03 | 导入后 1 家公司 | 内存中 2 家但磁盘 data.json 未落盘，包内只有 1 家 | **测试时序问题**。复测导出导入一致性通过 |
| P-02 | 授权对不上返回 2 家 | 测试直接改 `me.role`，但 `allowedCompanies()` 读的是 `SESSION.role`（仍是 admin） | **测试方法错误**。改用 staff 会话后返回 0，fail-closed 正常 |
| G-06 | `versions(...).map is not a function` | 测试代码漏写 `await` | **脚本 bug** |
| A-09 | （未执行）下钻越权 | 需真实切换受限账号会话 | 见第五节 |

## 五、未执行项及原因（不粉饰）

| 方案要求 | 状态 | 原因 |
|---|---|---|
| 100 公司 / 100 万流水 / 200 万日志 | ❌ 未执行 | 本软件为单文件 JSON + 全量内存加载架构，100 万流水约 300MB JSON，解析与渲染会耗尽内存。这是**架构上限**，非测试遗漏 |
| 2 万附件 / 10GB / 20GB 账套包 | ❌ 未执行 | 磁盘与时间不可行（20GB 打包预计数小时）；且 STORE 模式 ZIP 无压缩，体积即数据体积 |
| 挂后台 ≥8 小时 / 自动备份 72 小时 | ❌ 未执行 | 单次会话无法覆盖；需长期驻留环境 |
| 5–10 并发多用户 | ❌ 不适用 | 单机离线桌面应用，无服务端；多实例写同一 data 目录属设计外场景（已在手册声明不支持） |
| Windows 10 实机 / 125%·150% 系统缩放 | ❌ 未执行 | 本机为 Win11，系统缩放无法在自动化中模拟（仅能改视口尺寸） |
| 真实打印机分页 | ❌ 未执行 | 无打印机设备 |
| Google Drive 通道 | ❌ 未执行 | 需用户自备 OAuth 客户端（Client ID/Secret），当前仅完成代码级实现 |
| 云盘空间不足（507）/ 限速 | ⚠️ 仅代码级 | 有明确中文提示与日志，未构造真实场景 |
| 导入中断（断电/杀进程） | ⚠️ 仅代码级 | 有 `.rollback-<ts>` 快照 + `applyImport` 回滚，未做真实强杀 |

## 六、建议补充的测试用例（方案未覆盖）

按风险排序，前 6 条建议优先补：

| # | 用例 | 为什么重要 |
|---|---|---|
| 1 | **磁盘写满时保存账本** | 当前 `writeAtomic` 写临时文件后 rename，磁盘满会抛错但**界面是否提示**未验证。若静默失败 = 用户以为存了 |
| 2 | **两个实例同时打开同一数据目录** | 手册说不支持，但**没有锁文件**。两个实例会互相覆盖，且冲突副本机制只覆盖"文件被外部修改"，不覆盖"进程内覆盖" |
| 3 | **`data.bak.json` 是否真能救回** | 备份存在不等于能恢复。应实测：手动破坏 data.json → 启动 → 是否自动回退到 bak |
| 4 | **同一账套包重复导入 10 次** | 验证幂等性，不产生重复公司/重复附件 |
| 5 | **附件重名与中文/特殊字符名** | `20261028-143012_营业执照(1).pdf` 这类名字的归档与打开 |
| 6 | **闰年与跨年日期边界** | `2028-02-29`、`2026-12-31 → 2027-01-01` 的报表归属 |
| 7 | **金额浮点精度** | `0.1+0.2`、`1234.565` 四舍五入到分后是否与手算一致 |
| 8 | **超长文本显示** | 100 字分类名/公司名在表格、图表、PDF 打印中是否溢出 |
| 9 | **云盘文件被外部删除** | 版本索引仍在但云端没了 → 「恢复」应给出明确提示而非崩溃 |
| 10 | **导入包内公司 ID 与现有冲突** | 覆盖导入时若 ID 相同但内容不同，行为是否确定 |
| 11 | **主题/动效偏好迁移** | 账套包导入到新机器后，主题与动效设置是否保留（当前 system.json 有存，但导入未恢复 UI 偏好） |
| 12 | **版本池删除顺序** | 手动与自动混在同一分钟创建时，按 `at` 排序是否稳定（同秒时间戳可能导致删错） |

## 七、结论

- **功能层面**：22 项需求 + 新增需求 23 全部有对应用例并通过，未发现产品缺陷。
- **性能层面**：常规数据量下全部达标（切换 < 1s、下钻 < 1s、保存 < 2s、关闭弹窗 < 500ms）。
- **大数据与长期稳定性**：**未验证**。这是本次测试最大的空白，也是产品最大的未知风险。
- **权限矩阵**：仅验证了管理员与 fail-closed 逻辑，5 角色 × 9 操作的完整矩阵未跑（需多会话切换）。
- **建议**：在交付前至少补做第六节的第 1–3 条（磁盘满、双实例、bak 恢复），这三条都指向「数据可能静默丢失」，是资金软件的红线。
